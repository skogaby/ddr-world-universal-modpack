## CRITICAL: the task file's premise is wrong about the territory

Task-02 says the "multiplier derivation site and its toggle branch are
located" in `src/mods/real_speed_fix.rs`. **No Rust derivation exists.** The
real_speed_fix mod is three byte patches (R24/R25/R26) redirecting the NATIVE
`ddr::player::Option::SetScrollSpeed` divisor from Max BPM to Core BPM. The
derivation runs in game code. Req 33 therefore requires NEW glue (the
predecessor design specifies exactly this — raw reads + a derived-field
write). Fresh RE (Ghidra, gamemdx_20260721; spot-checked 20260616) resolved
every unknown the old design had flagged:

### The full consumer chain (all offsets verified on 20260721)

- `ddr::player::Option` (per side; `FUN_1801e9020(side_holder, 0)` →
  `*(ctx)+0xE0` — the SAME object as the assist-tick chain's
  `*(table[side])+0xE0`). Vtable base `0x180387978`:
  - `+0x8` speed TYPE (int): **0 = Real Speed mode** (player sets a target
    real speed), **1 = fixed-multiplier mode** (player sets ×speed directly).
    Getter = vtable+0x208 (`FUN_1800f4460`, trivial field read).
  - `+0xC` fixed multiplier ×100 (int; `SetHispeed` clamps [25,800], snaps 5).
  - `+0x10` DERIVED multiplier ×100 (int) — SetScrollSpeed's output:
    `clamp(trunc(target·100 / divisor), 25, 800)` where divisor = Max BPM
    (+0x90 double, capped) stock, Core BPM (+0x88 double) with the fix's R26
    cave. Clamp constants DAT_18035a740/744 = 25/800 (read from image).
  - `+0x14` real-speed TARGET (int).
  - `+0x80/+0x88/+0x90` = Min/Core/Max BPM (doubles) — vtable+0xB8
    (`FUN_1801e0d20`) is `SetBPMs(min,core,max)` and **immediately re-calls
    SetScrollSpeed** (vtable+0xD0) — so +0x10 is re-derived at chart load;
    any earlier write is clobbered.
  - vtable+0x218 (`FUN_1801e19d0`/`1801e1990`) = ACTIVE-multiplier getter:
    type 1 → +0xC, type 0 → +0x10.
- **The GamePlayActor (the judge-dispatch actor; side @+0x84, sound_offset
  @+0x16c — offsets already proven by assist_tick) latches the multiplier at
  actor construction** (`FUN_18005cce0` state 0, via `FUN_18005be90`):
  `+0x29C = vcall(Option vtable+0x218)` (int ×100), then
  `+0x290 = +0x294 = (float)multiplier / 100.0`.
- **Per frame (state 4) the actor re-writes the renderers from its own
  floats**: `speed = (int)(lerp(+0x290, +0x294, t) · 100)` →
  `SpotRenderer+0x28` AND `ArrowRenderer+0xA0` (the field mine_render/
  playfield_styling read). The lerp start-time is `+0x298`; `+0x290` is the
  current, `+0x294` the target (mid-song speed-change animation).
- Cross-build: the construction-tail store pair
  (`F3 0F 11 83 94 02 00 00  F3 0F 11 83 90 02 00 00`) matches exactly twice
  on BOTH 20260721 (18005cbf8/18005cc46) and 20260616 (18005cbb8/18005cc06)
  — the +0x290/+0x294 cluster is build-stable.

### Consequences

1. Writing Option+0x10 at first judge dispatch is INERT for arrows (the
   actor latched its own copy at construction). The correct write targets
   are the ACTOR's `+0x290/+0x294` floats (+`+0x29C` int) — the per-frame
   copy picks them up next frame.
2. The judge dispatch hands us the actor pointer directly — no
   player_option_table walk needed for the actor; the Option is reached for
   target/core/type via the table chain (side-indexed), same guarded pattern
   as assist_tick's `judgment_timing_ms`.
3. Req 33 applies to Real Speed MODE (type 0) only: fixed-multiplier mode
   has no BPM derivation (the old design: "keeps the player's selected
   target unchanged and derives its normalized multiplier" — target-derived
   mode). Type 1 sides are untouched.
4. "Regardless of the Real Speed Fix toggle": the toggle = that mod's
   config/mod-menu enable. The recompute must run even when the fix mod is
   DISABLED ⇒ it cannot live behind `real_speed_fix::enable()`. It CAN live
   in the mod's `init()` (registry runs init for every registered mod;
   only enable() is config-gated) — but the honest owner is the song-rate
   feature (the predecessor design assigns it to Song Playback Speed).

## Decided shape (recorded, auto mode)

- Pure math: `src/services/song_rate/real_speed.rs` —
  `rate_adjusted_multiplier(target, core_bpm, &RateSnapshot) -> Option<i32>`
  replicating the native derivation with the effective divisor
  `core_bpm × (source/output)`: f64 division + trunc + clamp[25,800]
  (byte-faithful to the native `(int)((double)(target*100) / divisor)`; the
  native cap-sentinel branch belongs to the Max-BPM path and does not apply
  to the Core path — same as the shipped R24 patch's semantics).
  `None` (no write) at identity/uncommitted or a non-finite/≤0 core BPM.
  Host tests in `real_speed_tests.rs`.
- Windows glue in the same file (clock_patch.rs precedent): a judge_hook
  pre-subscriber (Priority::Normal) + a scene callback, registered from
  `song_playback_speed`'s mod (the rate feature) at enable() — the fix
  toggle plays no part. Per side, once per song, at the first judge dispatch
  of that side's actor (post-commit, post-construction): read the side from
  actor+0x84, speed type/target/core via the Option chain; on Some(m) write
  actor+0x29C (int), +0x290/+0x294 (float m/100), and Option+0x10 (display
  consistency). Guards: null checks at every hop, value sanity (type ∈
  {0,1}, target in [25,800]·? — target range not clamped natively, guard
  core_bpm ∈ (0, 2000]), one WARN per session on an unreadable chain.
- 100 %/uncommitted: the subscriber does NOTHING (no reads beyond the
  snapshot + latch check) — both fix-toggle states keep today's behavior
  bit-identically because no code path writes anything.

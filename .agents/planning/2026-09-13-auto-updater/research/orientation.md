# Orientation: Auto-Updater

Blind-spot pass over the repository and the live GitHub release feed, done before
writing the decision register. Everything here is a fact with a citation, or is
marked as an implication.

## 1. What a release actually is

Source: `scripts/build_release_archive.sh`, the GitHub releases API
(`https://api.github.com/repos/skogaby/ddr-world-universal-modpack/releases`).

- **Archive layout is FLAT** — the zip root maps 1:1 onto the game folder (the
  folder holding `spice64.exe`). Root entries of the 2026-09-13 build:
  `ddr_world_hook.dll`, `mod-config.json`, `judgement_offsets.csv`, `README.md`,
  `data_mods/` (407 entries, 367 files — exactly the git-tracked `data_mods`
  set; `.DS_Store` is the only rsync exclude).
- The build script's comment claims `_cache/`, `*_ifs/`, `*.arc` are excluded
  but the rsync only excludes `.DS_Store`; this is harmless today because the
  repo checkout never contains `_cache/` or `*.arc`, and the committed `*_ifs/`
  dirs (`custom_options/select_music_option_lang_*_v3_ifs/`, `custom_folders/…`,
  `custom_series/…`, `music_wheel_song_length/…`) are INTENDED shipping content
  (generated by `scripts/gen_option_labels.py` and committed).
- The DLL in the archive is the **Windows 7 build** (`x86_64-win7-windows-msvc`,
  `-Z build-std=std,panic_abort`) because the default msvc target imports
  `ProcessPrng` from `bcryptprimitives.dll`, absent on Win7 — the loader rejects
  such a binary. **Any standalone Rust exe shipped to the same cabinets has the
  same constraint** (std's `HashMap` RandomState uses the same primitive).
- Release tags so far: `v1.0`, `v1.1`, `v1.2` (created 2026-08-27, 09-02,
  09-03). Each has **exactly one asset**, a zip named
  `ddr-world-universal-modpack-<datecode>[_suffix].zip` — the datecode is NOT
  derivable from the tag (`v1.2` → `…-20260903_hotfix.zip`, `v1.0` →
  `…-2026082600.zip`). Assets carry `size` and a `digest` field
  (`"sha256:<hex>"`), `content_type: application/zip`, and a
  `browser_download_url` under `github.com/…/releases/download/<tag>/<name>`.
- `GET /repos/{owner}/{repo}/releases/latest` returns the newest
  non-draft, non-prerelease release. Unauthenticated rate limit: 60
  requests/hour/IP — one boot = one API call (the asset download from
  `github.com` is not metered by the API limit).
- Release bodies are Markdown changelogs (could be shown by the updater).

## 2. How the DLL consumes the files the updater will touch

Source: `src/mods/config.rs`, `src/mods/per_song_judgement_offsets/{csv,store,bootstrap}.rs`,
`src/services/custom_options/ordering.rs`, `src/mods/decorative_option_headers.rs`.

### `mod-config.json`
- Located by **bare relative path** `mod-config.json` → process CWD
  (`config.rs:585,706`). Field `gamestart.bat` files do `cd /d %~dp0` before
  `start spice64.exe`, so CWD = the game folder.
- Parsed with `serde_json` **without `preserve_order`** (`Cargo.toml`): every
  DLL write re-emits the whole file with keys **sorted alphabetically at every
  level**, 2-space indent, no trailing newline, non-atomic (`save_json_key`,
  `config.rs:996-1014`). Unknown keys are tolerated on load (no
  `deny_unknown_fields`) and preserved on write.
- Implication: after the first in-game menu edit the user's file is
  alphabetical and reflowed; **line-oriented or order-preserving merges have
  no value to the DLL** — merge on the JSON tree.
- The DLL **writes** these sections at runtime (each replaced WHOLE by its
  writer): `mods` (every registered mod id → bool, on any Mods-tab toggle),
  `custom_options.p1`/`.p2`, `timing_offsets`, `fps_unlock`, `quick_restart`,
  `shader_fixes`, `s_marvelous`, `resolution`, `power_user_statistics`,
  `overlay_menu`, `smx_hardware` (incl. `p1card`/`p2card` — user card UIDs).
  These are unambiguously user-owned. Operator-only (never written) sections:
  `layeredfs`, `series_expansion`, `folder_expansion`, `diagnostics`,
  `player_perspective`, `assist_tick`, `song_playback_speed`, `training_mode`,
  `music_wheel_song_length`, `per_song_judgement_offsets`,
  `non_native_os_support`, `gameplay_timing_fixes`, and
  `custom_options.{persist_network,persist_json,lane_gamma_correction,preview_window,animate_backgrounds,option_menu_settings}`.
- Nested objects exist (`gameplay_timing_fixes.audio_clock.*`,
  `custom_options.*`) → "new key copied over" must be a **recursive** rule.
  Arrays other than `option_menu_settings` (`fps_unlock.presets`,
  `resolution.presets`, `series_expansion.custom_series`,
  `folder_expansion.custom_folders`, `layeredfs.allowlist/blocklist`) are
  plain values users may have customised.
- `mods`: a missing id defaults ON except `DEFAULT_OFF_MODS =
  ["smx-hardware","hide-bottom-text"]` (`mod_trait.rs:54-64`). The shipped
  `mod-config.json` is the maintainer's own config, so "release default" for a
  new mod = whatever value the maintainer committed (several are `false`:
  `series-expansion`, `folder-expansion`, `timing-offsets`,
  `non-native-operating-system-support`, `custom-resolution`). Copying a new
  `mods.<id>` key therefore CAN differ from the DLL's absent-key default — this
  is the intended "ships with the release's default" behaviour, but the
  maintainer should be aware the committed file is what users receive.
- Legacy migrations on load: `webui_options` → `custom_options.p1/p2` (deletes
  the legacy key); `custom_options.row_order` is no longer read (left in
  place); several parse-but-ignore keys. None conflict with an additive merge.

### `custom_options.option_menu_settings`
- Shape: `[{ "id": string, "overlay"?: bool, "in_game"?: bool }]`
  (`config.rs:66-78`). Ids matched case-insensitively; duplicates → first wins.
- **A "header" is just another row id** (`header_*`), registered as a real
  option by the `decorative-option-headers` mod (four ids today:
  `header_power_user_options`, `header_playfield_styling_options`,
  `header_training_options`, `header_profile_customization_options`).
  Grouping is purely by array position — there is no section object.
- Ordering rules (`ordering.rs:25-45`): listed ids first in listed order;
  **unlisted NON-header options fall to the END automatically**; **unlisted
  HEADER options are EXCLUDED entirely** (R10); unknown ids → one WARN, ignored.
- Implications: a new option that the updater does NOT insert still shows up
  (at the bottom, under the last header) — insertion under the right header is
  a quality improvement, not a correctness requirement. A NEW HEADER that the
  updater does not insert never renders at all — the updater MUST add missing
  headers. Ids the user has that the release no longer ships are harmless to
  keep (one WARN line).
- The DLL never writes this key, so the user's list is exactly what they (or a
  previous release) authored.

### `judgement_offsets.csv`
- Located by bare relative path `judgement_offsets.csv` (same CWD rule,
  `bootstrap.rs:27-28`).
- Grammar (`csv.rs:147-202`): optional header `code,p1_offset,p2_offset`
  (recognised only on line 1, case-insensitive `code`); LF or CRLF; cells
  trimmed; no quoting/comments; blank cell = unset; integers clamped to ±100;
  >3 cells or non-integer → line dropped; empty code → dropped; **duplicate
  codes → first occurrence wins**; per-side `code,,5` is legal.
- Writer (`csv.rs:204-221`, `bootstrap.rs:236-247`): header + rows in
  document order, LF, trailing newline, tmp+rename. Row order is **not
  semantically meaningful** (rows load into HashMaps).
- **The boot crawl appends a BLANK row for every musicdb basename not yet in
  the file** (`bootstrap.rs:83-139`, `csv.rs:106-121`). The shipped CSV
  (1462 lines) already ends with blank rows (`mmm,,`, `neno,,`, `buch,,`).
- Implication (the user likely has not considered this): after ONE boot, the
  user's CSV contains a row for every song, mostly blank. A strictly
  row-level "insert only missing songs" rule would then NEVER deliver a new
  community offset for an existing song. Only a **cell-level** rule ("fill
  blank cells from the release, never overwrite non-blank cells") propagates
  future community-list improvements while still protecting every value the
  user set. The only casualty is a user who deliberately hand-edited a value
  to blank — the in-game UI cannot produce a blank (offsets are a −100..+100
  scalar row), so that case is rare and hand-edit-only.
- The DLL's options-menu writer re-reads the file before every write
  (`bootstrap.rs:153`), so an updater rewrite between game sessions is safe.

## 3. What lives in `data_mods/` that the release did NOT ship

Source: grep of `./data_mods` write paths in `src/`.

- `data_mods/_cache/**` — all runtime caches (step-data `v1.bin`, shader
  synthesis, converted IFS textures, `training_hud`, `mod_menu`,
  `preview_overlay/*.arc`, `bg_preview/*.arc.hash`, atlas-cloner dirs). The
  README tells users to delete this dir on trouble; the LayeredFS scanner skips
  it.
- **Outside `_cache/`, inside shipped mod folders** (generated at enable /
  first boot): `texturelist.merged.xml` under every `<mod>/<x>_ifs/tex/`;
  `data_mods/s_marvelous/{dance_judge,dance_combo,scene_result,dance_fullcombo,select_music_card,select_music_side}_v3_ifs/`;
  `data_mods/custom_folders/select_music_folder_v3_ifs/{geo,afp,…}` +
  `.cache_meta.json`; `data_mods/bg_preview/**` (an entire generated mod
  folder); any `*.arc`.
- **User-owned content**: `layeredfs.mod_folder` defaults to `./data_mods`, so
  users drop their OWN mod folders (custom song packs, texture packs) directly
  under `data_mods/`.
- Implication: a naive "mirror the release's `data_mods/` and delete
  extraneous files" would destroy user mods and force first-boot regeneration.
  A naive "overlay only, never delete" leaves stale shipped files behind —
  which is a real hazard here: AGENTS.md warns that a stray
  `seop_op_item_*.png` under `data_mods/custom_options/` gets packed back into
  the served atlas by LayeredFS texture injection (that is exactly why those
  150 files were removed in 2026-08). Correct pruning needs to know **which
  files the PREVIOUS release installed** — i.e. the updater must keep an
  install manifest.

## 4. Versioning state on disk

- **There is no installed-version marker anywhere.** `Cargo.toml` version is
  `0.1.0` (never bumped), no `build.rs`, no `CARGO_PKG_VERSION`/`GIT_HASH` use.
  The only version string is the hardcoded splash `"DDR World Universal
  Modpack v1.2"` (`src/lib.rs:649`, render-thread widget, not logged).
- Implication: the updater must introduce its own marker (and could, as a
  follow-up, become the source of truth the DLL's splash reads).

## 5. Launch integration facts

- README install step 3: add `-z ddr_world_hook.dll` to the spice2x launch
  options "in `gamestart.bat`". No `gamestart.bat` template exists in the repo.
  Field `.bat` files seen in research notes:
  `.\spice64.exe -modules modules -ddr -w -p <PCBID> -url … -icmphook -K ddr_world_hook.dll`
  preceded by `cd /d %~dp0`.
- In a batch file, invoking an `.exe` directly (without `start`) blocks until
  it exits — the "game won't start until the updater finishes" requirement is
  satisfied by placing the updater line above the spice line.
- Platforms: Windows 7/10/11 cabinets AND macOS/Linux under CrossOver/Wine
  (the modpack is developed under CrossOver) — the updater runs under Wine too.
- Cabinets often boot straight into `gamestart.bat` unattended → the updater
  must be **non-interactive and must never block the game** on network or
  update failure.

## 6. Toolchain facts relevant to a standalone exe

- Nightly toolchain pinned (`rust-toolchain.toml`, targets
  `x86_64-pc-windows-msvc` + `x86_64-win7-windows-msvc`, `rust-src`); builds
  cross-compiled from macOS via `cargo xwin` (0.21.4 installed; clang-cl/lld
  cached). `trim-paths = "all"` strips builder paths from binaries.
- Pure modules are host-tested with plain `cargo test`; engine-facing code
  is not — a standalone updater crate with no `retour` dependency can be
  fully host-tested on macOS.
- TLS risk: GitHub requires TLS 1.2+. Unpatched Win7 (WinHTTP/schannel) lacks
  TLS 1.2 by default (needs KB3140245 + registry). A Rust client using
  `rustls` with bundled `webpki-roots` avoids both the OS TLS stack and the
  (possibly stale) OS root store. Whether `rustls` + `ring` links under the
  tier-3 win7 target with `-Z build-std` is being verified by the prototype in
  `prototypes/win7-tls-probe/` (result recorded in `research/technologies.md`).
- Self-replacement: Windows forbids overwriting/deleting a running exe but
  allows RENAMING it; the standard self-update dance is rename-old → write-new
  → delete-old-on-next-run. Wine behaves the same.

## 7. Unknowns carried into the register

1. Product shape: one exe in the game folder, invoked by name from
   `gamestart.bat`; should it also ship inside the release zip (⇒ self-update)?
2. Version identity: marker file vs. hashing; "different from installed" vs.
   "newer than installed".
3. `data_mods` sync semantics: overlay + manifest-based pruning (recommended)
   vs. overlay-only.
4. CSV merge granularity: cell-level (recommended, see §2) vs. row-level as
   literally stated.
5. `option_menu_settings` insertion algorithm details (sibling-anchored vs.
   section-end; missing header handling).
6. Failure policy: exit codes, rollback, timeouts; interactive vs. silent.
7. Build/release integration: separate crate vs. workspace member; how
   `build_release_archive.sh` includes the exe.
8. Whether the DLL should learn to read the new version marker (follow-up).

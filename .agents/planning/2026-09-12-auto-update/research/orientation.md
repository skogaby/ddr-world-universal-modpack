# Orientation: Auto-Update

Blind-spot pass over the idea and the territory it lands in. Everything below was
verified against the tree on 2026-09-12 (paths repo-relative; `file:line` cites).

## 1. What the idea asks for

After every mod has initialized, check GitHub's latest release for this repo; if it
is newer than the running build, download the release zip, install the DLL,
`data_mods/`, and merge `mod-config.json` (new keys in, existing values win), showing
a bottom-of-screen progress bar + "DDR World Universal Modpack - Update In Progress",
then prompt the user to restart.

## 2. Where "all mods are done initializing" is

`src/lib.rs::init()` runs on a thread spawned from `DllMain` (`src/lib.rs:32-45`) —
NOT the loader thread, and the game keeps booting underneath it. The sequence is
load-bearing (AGENTS.md); the point the idea names is the "ready" line:

```rust
// src/lib.rs:602-605
log_info!("DDR World Hook DLL ready. {} mod(s) active.", enabled_count);
profiling::tick("init_complete");
profiling::dump_scan_stats();
```

Everything after that is the splash-screen thread spawn (`:608-688`) and `init()`
returns. There is **no existing "boot complete" event/latch** any module subscribes
to — the updater would be the first consumer, so a tiny post-init notifier (or a
direct call from lib.rs at that line) is needed. Mods' `enable()` runs at step 8
(`:561-565`), BEFORE the ready line, so the updater's `enable()` alone cannot be the
trigger point.

Some mods spawn background work from `enable()` that may still be running at the
ready line (asset generation, fast_bootup verifier, mod-menu chrome synthesis). None
of it conflicts with a network check.

## 3. What the release archive contains

`scripts/build_release_archive.sh` stages: `ddr_world_hook.dll` (the
`x86_64-win7-windows-msvc` build — runs on every Windows version), `mod-config.json`,
`judgement_offsets.csv`, `README.md`, and `data_mods/` (rsync with ONLY a `.DS_Store`
exclude — the comment claims `_cache/`, `*_ifs/`, `*.arc` exclusions that the command
does not implement; the maintainer's tree happened to have none of those at archive
time). Output name `ddr-world-universal-modpack-YYYYMMDD.zip`; the live v1.2 asset was
hand-renamed `…-20260903_hotfix.zip`, so the asset NAME is not a stable identity.

`data_mods/` is 3.4 MB / 367 tracked files; the archive is 6.4 MB. The
`custom_options/*_ifs/tex/*.png` option-label textures ARE tracked and shipped
(generated by `scripts/gen_option_labels.py`); the `s_marvelous/*_ifs/` dirs are
enable-time generated and must never ship; `data_mods/_cache/` is runtime state.
⇒ the installer must OVERLAY `data_mods/` (add/replace), never mirror-delete.

Live release metadata (GitHub REST `releases/latest`, fetched 2026-09-12):
`tag_name: "v1.2"`, one asset, `content_type: application/zip`, `size: 6396575`,
`browser_download_url` on `github.com/.../releases/download/v1.2/...` (302 → CDN),
and a `digest: "sha256:…"` field on the asset (GitHub added asset digests in 2025).
`/releases/latest` already excludes drafts and prereleases.

## 4. Version identity — there is none today

- No `build.rs`, no `env!("CARGO_PKG_VERSION")` use; `Cargo.toml` says `0.1.0`.
- The ONLY version string is the hardcoded splash text `"DDR World Universal Modpack
  v1.2"` (`src/lib.rs:624`). It is not logged.
- A release cannot be compared to the running build without introducing one.

Traps: (a) forgetting to bump the compiled version when tagging would make the updater
re-download the "newer" release on every boot — an infinite loop unless something else
(an installed-asset stamp) breaks it; (b) hotfix re-uploads under the same tag (as
happened for v1.2) are invisible to tag comparison alone.

## 5. Install paths

Everything the DLL touches is **CWD-relative** (the CWD is the game folder holding
`spice64.exe`): `mod-config.json` (`src/mods/config.rs:545`), `./data_mods`
(`src/services/avs_layeredfs/mod.rs:51-53` + many hardcoded `./data_mods/...`
constants), `judgement_offsets.csv` (`per_song_judgement_offsets/bootstrap.rs:28`).
The DLL never resolves its own file path; `crash_handler::record_dll_bounds()` gets its
HMODULE via `GetModuleHandleExW(FROM_ADDRESS)` but stores no path. Replacing the DLL
needs `GetModuleFileNameW` on that handle (users may pass any `-k <name>.dll`).

## 6. Replacing a loaded DLL

The image file of a loaded module cannot be opened for write, but it CAN be renamed on
the same volume: both the Windows loader and Wine's (`dlls/ntdll/loader.c`
`open_dll_file`: `NtOpenFile(... FILE_SHARE_READ | FILE_SHARE_DELETE ...)`, verified
in wine-mirror master) open images with `FILE_SHARE_DELETE`, which is what permits
`MoveFileEx` on the mapped file. Standard self-updater shape: rename
`ddr_world_hook.dll` → `ddr_world_hook.dll.old`, write the new file at the original
path, delete `.old` on the next boot. Deleting the running file outright fails on
Windows (mapped image) — so the `.old` file must be cleaned up by the NEXT process.
Consequence: a DLL swap is only ever effective after ONE restart — "stage now, apply
at next boot" for the DLL would cost TWO restarts, so the DLL swap must happen
in-session.

## 7. Networking capability — none today

`Cargo.toml` has no HTTP crate and the `windows` crate feature list lacks
`Win32_Networking_WinHttp`; `src/` has zero hits for winhttp/wininet/TcpStream/`https://`.
Options: WinHTTP via the `windows` crate (system TLS, zero new crates; Wine implements
winhttp incl. `WINHTTP_OPTION_SECURE_PROTOCOLS`, redirect policy, timeouts — verified
in `dlls/winhttp/session.c`; Win7 needs TLS 1.2 forced explicitly and may fail on
un-updated cabinets → fail-open) vs a pure-Rust stack (`ureq`+`rustls`+`webpki-roots`:
+2 MB DLL, `ring` cross-compile under cargo-xwin/`-Z build-std`, but no OS cert/TLS
dependence). GitHub API needs a `User-Agent`; unauthenticated limit 60 req/h/IP.

## 8. Archive extraction / integrity

No zip reader in the tree (`core/arc.rs`, `core/ifs.rs`, `core/ap2/` are game formats).
`flate2` + `miniz_oxide` + `crc32fast` are already in `Cargo.lock` (via `image`), so a
minimal central-directory ZIP reader (stored + deflate, CRC32-checked, path-sanitised)
costs no new transitive deps; the `zip` crate is the alternative. ZIP entries carry
CRC32 — combined with TLS + Content-Length, end-to-end integrity is covered without a
local SHA-256; the GitHub `digest` string is still useful as an *identity* to record.

## 9. UI primitives

- Logical canvas 1280×720, origin top-left; Custom Resolution never changes it.
- `TextWidget` (`src/widgets/text_widget.rs`): `set_text/position/scale/color(f32×4)/
  alignment(Center about x)/outline/show/hide`; no width query, but `Center` alignment
  at x=640 gives exact centering natively. Render-thread only
  (`widget_renderer::run_on_render_thread`, `src/services/widget_renderer.rs:676`).
- `ImageWidget` (`src/widgets/image_widget.rs`): needs a texture; `set_size(w,h)`
  stretches it — the mod menu draws its scrollbar thumb, selection bar and header bars
  exactly this way from a 64×16 synthesized WHITE strip texture
  (`src/mods/mod_menu/chrome.rs:149-163`, published by `chrome_loader::status()`, kicked
  at mod-menu `enable()` so it is resident ~0.7 s into boot). A progress bar = two
  stretched, tinted strip sprites. `STRIP_TEX` is `pub(super)` today — needs a
  `pub(crate)` accessor. Fallback: text-only percentage.
- `services/toast` is a single shared gold widget at (640, 630) — any other mod's
  flash/dismiss supersedes it; not suitable for a live-updating progress label.
- Widget nodes are never reclaimed (`destroy()` = hide) — create once, reuse.
- `input_manager::on_frame` callbacks run on the render thread once per frame (top of
  the frame pump) — the idiomatic "poll atomics, mutate widgets" seam.
- Exclusive input + modal pattern: `mod_menu/mod.rs:419-426`
  (`set_exclusive_consumer` + `set_input_suppressed`). No yes/no dialog primitive.
- Process exit precedent: `smx_hardware/touch.rs:565-597` (`TerminateProcess` after
  1.5 s; graceful CRT exit wedges under Wine). Nothing relaunches the game.
  spice2x's SpiceAPI has `control restart`, but only over TCP when `-api` is enabled.

## 10. Config file facts that shape the merge

- `mod-config.json` is parsed into a typed `ConfigFile` (`src/mods/config.rs:610-658`,
  unknown keys dropped in memory, preserved on disk only because every writer does a
  fresh `Value` read-modify-write). Read ONCE at step 0 — disk-only changes land next
  boot.
- `serde_json` `preserve_order` is NOT enabled → every write re-sorts keys
  alphabetically; the shipped file is hand-ordered and has never been rewritten by the
  DLL.
- Writers: `save_json_key` (whole-section replace, no tmp+rename, unparseable file ⇒
  `{}`), `save_mod_states` (whole `mods` map from the registry — drops ids it doesn't
  know), `save_custom_options_values` (per-side). A DLL-written section re-emitted by
  the OLD build after a merge drops keys only the NEW build knows ⇒ merge is safest
  when performed by the new build before any writer runs (boot step 0, before
  `config::init()`).
- Closest prior art: `migrate_webui_options_to_custom_options` (`config.rs:847-900`).
- Nesting: depth-3 objects (`custom_options.p1/p2.<id>`,
  `gameplay_timing_fixes.audio_clock.*`); arrays (`option_menu_settings[]`,
  `custom_series[]`, `presets[]`). A shallow top-level merge would add NOTHING (every
  top-level key already exists locally) — recursion into objects is required; arrays
  and scalars must be leaves (local wins); `custom_options.p1/p2` are per-player caches
  and should be treated as opaque leaves.
- The shipped default currently carries maintainer-specific values
  (`persist_network: false`, `lane_gamma_correction: 3.0`, `movie_mode: "fallback"`,
  `mirror_players: true`, custom series/folders) — a merge would propagate those into
  users' configs wherever the key is missing. Release hygiene item.

## 11. Second-restart wrinkle

`atlas_cloner::atlases_rebuilt_this_boot()` (`src/services/avs_layeredfs/atlas_cloner.rs:42-47`)
already drives a red "REBOOT THE GAME AT LEAST ONCE" splash whenever PNG inputs changed.
Any update that touches `data_mods` PNGs will, on the first boot with the new files,
rebuild atlases and show that warning — i.e. two restarts total. Unavoidable without
pre-warming the atlas cache against staged inputs (invasive; Phase 2 candidate).

## 12. Platform notes

- Wine/CrossOver detection: `core::platform::running_under_wine()`.
- The shipped DLL is the Win7 build; WinHTTP exists on Win7 but TLS 1.2 must be
  requested explicitly (`WINHTTP_OPTION_SECURE_PROTOCOLS`) and depends on OS updates +
  root store freshness — fail-open with one WARN is the only sane policy.
- Many cabinets are offline or on restricted networks: the check must fail QUIETLY
  (one INFO) and quickly (short connect timeout).

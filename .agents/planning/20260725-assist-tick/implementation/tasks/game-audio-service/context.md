## Ambiguities found, and how they are resolved

1. **Requirement 12 asks for "the cue index resolved" to be logged, but `se_play` does not return
   it.** Resolved by calling `IXACT2SoundBank::GetCueIndex` (vtable `+0x00`, one of the three
   indices design §4.1 sanctions) on the **first** play of a given cue name and logging the result
   at **info**. It is info rather than warn so that AC9's "exactly one warning for the whole
   session" still holds when the cue does not exist — the single warning is the one the play
   sentinel emits. This needs no change to the design's public API: the sound-bank pointer is kept
   in the service's own registry, keyed by slot, and `BankHandle` stays `{ slot: i32 }`.
2. **Where the scaffolding's file IO happens.** Reading the two bank files inside the judge callback
   would put ~5.7 KB of blocking IO on the game thread's hot path (CLAUDE.md rule 7). Resolved by
   reading them at `install()` time on the init thread — which is also what design §4.2 specifies
   for the real mod's `init`, so the scaffolding rehearses the final shape rather than diverging
   from it. `install()` calls no game function, so the init-thread rule (§3.3) is respected.
3. **Where `game_audio::init` goes in `lib.rs`.** It needs only signature resolution (step 3), but
   it is placed immediately **after** `judge_hook::init` because the Step-2 scaffolding subscribes
   to that dispatcher. Recorded in a comment at the call site; Step 3 makes the ordering
   irrelevant.
4. **Leaking on a failed creation.** The buffers must be leaked *before* the create calls so the
   pointers handed to the engine are stable. If a create then fails, ~5.7 KB stays leaked for the
   process lifetime. Accepted deliberately (one-shot, bounded) and commented, rather than
   introducing a free path that could hand the engine a dangling pointer.
5. **`register_bank` holds the service mutex across engine calls.** Consistent with
   `asset_loader`, and permitted: CLAUDE.md rule 6 forbids holding a lock across a
   `run_on_render_thread` *schedule*, which this never does.

## Non-functional expectations

- Panic-free everywhere a hook callback can reach: no `unwrap`/`expect`, no indexing, no panicking
  slicing. `Mutex::lock()` handled with `.ok()?` / `match`.
- Every failure path: exactly one warning, no crash, nothing else affected (design §6's table).
- No new crate dependency, no config section, no game data files touched.
- `unsafe` scoped narrowly around the raw reads/writes and the vtable dispatches.

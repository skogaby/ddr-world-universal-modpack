## Implementation approach

One file changes: `ddr-chart-tools/src/xsb/mod.rs`.

### The seam

The song and SE profiles differ in exactly three things — which sound entries are emitted, how
many cues point at them, and what those cues are named. Everything else (header constants, the
64-byte name fields, the 16-bucket hash table, the name index, the CRC) is common. So the seam
is a single descriptor, resolved once and threaded through layout and emission:

```rust
// reference shape only — see the implementation for the real thing
struct Profile {
    /// Sound entries, in file order. Byte templates.
    sounds: &'static [&'static [u8]],
    /// Cues, in file order: (index into `sounds`, cue-name suffix).
    cues: &'static [(usize, &'static str)],
}
```

- **Song** = `sounds: [COMPLEX_SOUND_BYTES, SIMPLE_SOUND_BYTES]`, `cues: [(0, "_s"), (1, "")]`
  — preview cue first, pointing at the complex sound, exactly as today.
- **SE** = `sounds: [SE_SIMPLE_SOUND_BYTES]`, `cues: [(0, "")]`.

This is preferred over an `enum Profile { Song, SoundEffect }` with `match` arms at each of the
four emission sites, because the descriptor removes the branching entirely: `Layout::compute`
sums the sound lengths and the cue-name lengths, and the emitters loop. Rejected alternative:
duplicating `build_xsb` into `build_xsb_se`, which the task file explicitly warns against
("do not duplicate the whole builder") and which would let the two paths' CRC/hash handling
drift.

Byte-identity for the song path falls out of the descriptor being the same data in the same
order — verified by a golden test rather than by argument (see S9).

### The SE sound entry

Fixed 12-byte template, from research §5.6/§8.3 with `wave_index` amended to 0 per the design's
2026-07-25 amendment:

```
00 | 06 00 | FE | 00 00 | 00 | 0C 00 | 00 00 | 00
^flags       ^cat  ^vol   ^pitch ^prio ^len   ^wave  ^wavebank
```

Named constants for category (6) and volume (0xFE) with the stock precedent cited, so the
values are auditable without re-reading the research note.

### Layout consequences (SE, 4-character name)

| Section | Offset | Size |
|---|---|---|
| Header | `0x00` | `0x4A` |
| Soundbank name | `0x4A` | 64 |
| Wavebank name | `0x8A` | 64 |
| Sound entries | `0xCA` | 12 |
| Simple cues | `0xD6` | 1 × 5 |
| Hash table | `0xDB` | 16 × 2 |
| Name index | `0xFB` | 1 × 6 |
| Cue names | `0x101` | 5 (`"asti\0"`) |
| **Total** | | **262** |

Hand-checked against all 23 validator rules in research §5.5 — recorded in `context.md`.

### Order of work

1. Add the song-profile golden regression test **first** (bytes already captured from the
   pre-change build), so the byte-identity guarantee is armed before the refactor.
2. Add the SE tests. They must fail to compile / fail against the absent `write_se`.
3. Introduce the profile descriptor, port the song path onto it, confirm the golden still
   passes and the 305 existing tests still pass.
4. Add `write_se` and the SE sound template; make the SE tests pass.
5. Separately: repair the two pre-existing clippy lints (see `progress.md` → Deviations).
6. Gates.

and a silently moved song byte. It is written before the refactor, from bytes captured off the
unmodified build.

## Risks

| Risk | Mitigation |
|---|---|
| Refactoring shared internals shifts a song byte | S9, armed before the refactor |
| A validator rule objects to a single-cue/single-sound bank | All 23 rules hand-checked (`context.md`); S2/S4/S6/S7 assert the offset-cursor and bucket rules directly. Documented fallback in the plan is the two-entry shape — but that is a *wave-bank* fallback, and the SE sound bank's `wave_index` is a one-constant change either way |
| `wave_index` silently wrong (0 vs 1) — the exact trap that made research use two wave entries | S3 asserts it explicitly; task 02 asserts the pair agrees |
| Pre-existing clippy failure masks a new one | Baseline captured before any edit; the two known errors are named in `context.md` |

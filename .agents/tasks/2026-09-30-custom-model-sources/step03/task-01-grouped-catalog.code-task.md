# Task: Source-grouped catalog

## Description
Regroup the option-row catalog (`src/mods/background_dancers/catalog.rs`) by source — STOCK first,
then every custom source — with the accessor set the rows and the pick path will index, while a
throwaway flat view inside `options.rs` keeps today's two rows byte-for-byte unchanged until Step 4.

## Background
`Catalog { dancers, stages }` is one flat list per kind (stock block byte-sorted by key, custom block
sorted by label then key). `build_catalog_with_custom(stages, dancers, &[(key, label)])` is fed from
`mod.rs::enable` through the Step 2 adapter. Sources now arrive as `sources::CustomEntry`.

## Technical Requirements
1. `SourceCatalog { slug: Option<String> /* None = STOCK */, label, entries }`;
   `Catalog { dancers: Vec<SourceCatalog>, stages: Vec<SourceCatalog> }` with `sources(kind)`,
   `has_custom(kind)`, `source_count(kind)`, `source_label(kind, value)` (0 RANDOM · 1 STOCK · 2… custom),
   `count(kind, source)`, `entry(kind, source, value)`, `label(kind, source, value)` (RANDOM for 0),
   `key(kind, source, value)`, `keys(kind, source)`.
2. `build_catalog(stages, dancers)` = stock only (one source per kind, label `STOCK`);
   `build_catalog_with_custom(stages, dancers, custom: &[CustomEntry])`: STOCK source byte-identical
   to `build_catalog`'s; custom entries whose key is a candidate of that kind grouped by `source.slug`
   (label from the entry's `source.label`), sources sorted by `(label, slug)`, entries within a source
   sorted by `(label, key)`, dedup by key, labels fitted to 15 bytes.
3. `Catalog::flat_entries(kind) -> Vec<CatalogEntry>`: STOCK entries followed by every custom entry
   sorted by `(label, key)` — exactly today's flat list (the Step 3 shim's input).
4. `clamp_to_catalog` unchanged.
5. `mod.rs::enable` drops the Step 2 adapter and passes `&lifecycle::custom_entries_snapshot()`.
6. `options.rs` SHIM: `register(built: Catalog)` builds a private flat view from `flat_entries` and
   registers today's two rows over it (labels, clamp, choices unchanged); marked `// Step 4 replaces`.

## Acceptance Criteria

1. **STOCK unchanged**
   - Given the real stock rows
   - When `build_catalog` and `build_catalog_with_custom(.., &[])` run
   - Then `sources(kind)[0]` has label `STOCK`, `slug None`, 26 dancers / 25 stages with today's labels and key ↔ value pairing; `has_custom` is false

2. **Grouping and order**
   - Given custom entries in sources `UMX2`, `DDR STRIKE`, `CUSTOM` (out of order, two entries with the same label in one source)
   - When `build_catalog_with_custom` runs
   - Then `sources(Dancer)` is `[STOCK, CUSTOM, DDR STRIKE, UMX2]`, `source_label(kind, 0..=4)` reads `RANDOM, STOCK, CUSTOM, DDR STRIKE, UMX2` and `None` at 5, entries within a source are sorted by label then key, `keys(kind, i)` lists that source's keys in row order

3. **Non-candidate keys dropped; kinds separated**
   - Given a custom entry whose key is no candidate, and a dancer-only source
   - When built
   - Then the ghost entry is absent and the dancer-only source does not appear under `stages`

4. **Flat view is today's list**
   - Given the fixture of the existing `custom_entries_append_after_the_untouched_stock_block` test
   - When `flat_entries(kind)` runs
   - Then it equals the list the old builder produced (stock block, then `PETER GRIFFIN`, `ZED`; stage `GRIFFIN HOUSE`)

5. **Gate**
   - Given the change
   - When the background_dancers harness and `cargo check --target x86_64-pc-windows-msvc` run
   - Then both are clean

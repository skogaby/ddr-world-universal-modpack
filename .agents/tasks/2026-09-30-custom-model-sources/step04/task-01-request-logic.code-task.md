# Task: Pure request logic for the source rows

## Description
Factor everything the option rows decide from plain values into a dependency-free file
`src/mods/background_dancers/options_logic.rs`: the row table (ids, kinds, roles) built from the
grouped catalog, the mapping from a side's `(source value, model value)` to a pick `Request`, the
key a focused row previews, and the per-row load clamp bound.

## Background
`options.rs` callbacks are plain `fn` pointers, so per-row data must be looked up by id in a
process-wide table. The engine-facing registration cannot be host-tested, but this mapping can.

## Technical Requirements
1. `RowRole { Source, Model { source: usize } }`; `RowInfo { id: String, kind: Kind, role: RowRole }`;
   `build_rows(cat: &Catalog) -> Vec<RowInfo>` — per kind: the source row first when
   `has_custom(kind)`, then one model row per source in catalog order (`sources::model_row_id` /
   `source_row_id` over the base ids `background_dancer` / `background_stage`).
2. `Request { Any, Within { source: String, keys: Vec<String> }, Key(String) }`.
3. `request_for(cat, kind, source_value: Option<i32>, model_value_of: impl Fn(&str) -> Option<i32>)
   -> Request`: no source row (`None`) ⇒ STOCK semantics (source index 0); `Some(0)` ⇒ `Any`;
   `Some(v ≥ 1)` ⇒ source `v − 1`: model `0` ⇒ `Within { label, keys }`, `k ≥ 1` ⇒ `Key`; anything
   out of range ⇒ `Any`.
4. `row_choice_key(cat, rows, id, side_values: impl Fn(&str) -> Option<i32>) -> Option<String>`:
   model row ⇒ its own value's key; source row ⇒ the effective pick (the selected source's model row
   value's key), `None` for RANDOM at either level.
5. `row_max(cat, rows, id) -> Option<usize>`: the source row's `source_count`, a model row's `count`.
6. `label_for_row(cat, rows, id, value) -> Option<String>`: source row ⇒ `source_label`, model row ⇒
   `label(kind, source, value)`.
7. Harness-mounted (`scripts/validate_background_dancers.sh`); `mod.rs` declares it.

## Acceptance Criteria

1. **Row table**
   - Given a catalog with dancer sources `[STOCK, CUSTOM, DDR STRIKE]` and stock-only stages
   - When `build_rows` runs
   - Then the rows are `background_dancer_source` (Source), `background_dancer` (Model 0),
     `background_dancer_custom` (Model 1), `background_dancer_ddr_strike` (Model 2), `background_stage`
     (Model 0, no stage source row)

2. **Requests**
   - Given that catalog
   - When `request_for` runs with `(None, stock value 3)`, `(Some(0), _)`, `(Some(3), 0)`, `(Some(3), 2)`,
     `(Some(9), _)`, `(Some(3), 99)`
   - Then it yields `Key(stock entry 3)`, `Any`, `Within { "DDR STRIKE", its keys }`, `Key(entry 2 of DDR STRIKE)`,
     `Any`, `Any`

3. **Preview key**
   - Given side values `source = 3`, `background_dancer_ddr_strike = 1`, `background_dancer = 5`
   - When `row_choice_key` runs for each row id
   - Then the source row and the DDR STRIKE row both yield DDR STRIKE's first key, `background_dancer`
     yields stock entry 5, and with `source = 0` the source row yields `None`

4. **Bounds and labels**
   - Given the rows
   - When `row_max` / `label_for_row` run
   - Then the source row has max 3 and labels `RANDOM, STOCK, CUSTOM, DDR STRIKE`; a model row has its
     source's count and `RANDOM` at 0; an unknown id yields `None`

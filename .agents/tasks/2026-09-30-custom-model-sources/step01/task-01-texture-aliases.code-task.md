# Task: Texture aliases on custom-option rows

## Description
Add two optional aliases to `RegisterSpec` so a registered row can render another row's label
texture (`seop_item_<alias>`) and preview chrome (`seop_image_<alias>`) instead of the ones derived
from its own id. No existing row changes behaviour.

## Background
The Background Dancers mod is about to register one model row per custom-content source
(`background_dancer_<slug>`), and every one of them must show the shipped `BACKGROUND DANCER` label
and the dancer preview chrome. Today `RegisteredOption::label_texture_name()` and
`preview_image_base_name()` are `format!("seop_item_{id}")` / `format!("seop_image_{id}")`, and
`register_option` registers the atlas label entry under the id. The atlas registrars already
deduplicate by name, so N rows sharing an alias cost one atlas slot.

## Technical Requirements
1. `RegisterSpec` gains `label_texture_like: Option<&'static str>` and
   `preview_texture_like: Option<&'static str>` (default `None` in every builder) plus chainable
   setters `label_texture_like(id)` / `preview_texture_like(id)`.
2. `RegisteredOption` carries both; `try_register` copies them.
3. `RegisteredOption::label_texture_name()` returns `seop_item_<alias>` when the label alias is set,
   else the current name; `preview_image_base_name()` likewise with `seop_image_<alias>`.
   `preview_image_name_for_value` / `preview_image_names` keep building on the base name.
4. `register_option` registers the label atlas entry under the label stem (alias or id).
5. Update the `RegisterSpec` doc comment (where `seop_item_<id>` is described) to mention the aliases.

## Dependencies

## Implementation Approach
1. Write the registry tests first (alias set / unset) in the existing `registry.rs` test modules or a
   sibling test file mounted by `scripts/validate_custom_options.sh`.
2. Add the fields + setters in `src/services/custom_options/api.rs`; copy them in
   `src/services/custom_options/registry.rs::try_register`; change the two name functions.
3. Pass the label stem in `src/services/custom_options/mod.rs::register_option`.

## Acceptance Criteria

1. **Alias resolution**
   - Given a registered option with `label_texture_like("background_dancer")` and
     `preview_texture_like("background_dancer")`
   - When `label_texture_name()`, `preview_image_base_name()` and `preview_image_names()` are read
   - Then they return `seop_item_background_dancer`, `seop_image_background_dancer` and
     `[seop_image_background_dancer]` regardless of the option's own id

2. **No alias, no change**
   - Given a registered option without aliases
   - When the same functions are read
   - Then they return the id-derived names (the existing header test `seop_item_hdr_preview` still passes)

3. **Independent aliases**
   - Given an option with only `preview_texture_like` set
   - When the names are read
   - Then the label is id-derived and the preview is the alias

4. **Harness green**
   - Given the change
   - When `./scripts/validate_custom_options.sh` runs
   - Then every test passes, and `cargo check --target x86_64-pc-windows-msvc` is clean

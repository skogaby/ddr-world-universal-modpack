# Task: `ScalarFormat::Dynamic` — owner-supplied per-value text for scalar rows

## Description
Add a new `ScalarFormat::Dynamic(DynamicLabelFn)` variant to the custom-options framework so a
scalar row can render arbitrary per-value names (`RANDOM`, `EMI #2`, `BOOM #3`, …) through the
game's own text value layer, and thread the option id into the two scalar formatters so the
labeler can dispatch on it. Purely additive to `src/services/custom_options/`.

## Background
The in-game options menu can only render TEXT values through a Scalar row (Enum rows are chip
textures). Today's `ScalarFormat` variants compose a prefix/suffix around the integer; `Labeled`
has exactly one terminal label. The Background Dancer / Stage rows need a name per value from a
runtime-discovered catalog, so the formatter needs a fn-pointer hook (design §4.1). `ScalarFormat`
must stay `Copy + Debug` (fn pointers are both). The value text budget is ≤ 15 bytes (MSVC SSO in
the game's `std::string`; longer heap-promotes and leaks per push — see `destruct_sso_string` in
`rows.rs`).

## Technical Requirements
1. `pub type DynamicLabelFn = fn(option_id: &str, value: i32) -> Option<String>;` in `api.rs`.
2. `ScalarFormat::Dynamic(DynamicLabelFn)` with a doc comment stating the ≤ 15-byte / no-panic /
   no-block contract and the `None` ⇒ plain integer fallback.
3. `format_scalar_value(id: &str, value: i32, format: ScalarFormat) -> Vec<u8>` and
   `format_scalar_value_utf8(id: &str, value: i32, format: ScalarFormat) -> String` gain the id
   parameter; every other variant's output is byte-identical to today.
4. `Dynamic(f) => f(id, value).unwrap_or_else(|| value.to_string()).into_bytes()`.
5. Both call sites pass the option's id (`opt.id`).
6. All existing tests updated for the new signature; new tests for the `Dynamic` arm (label hit,
   `None` fallback, id dispatch, UTF-8 twin parity).
7. `./scripts/validate_custom_options.sh` stays green (it mounts `api.rs` + `registry.rs` +
   `scalar_format_tests.rs` in a host crate — the formatter must stay dependency-free).

## Implementation Approach
1. Write the failing tests first: in `scalar_format_tests.rs` a `dynamic_labeler_and_fallback`
   test with a local `fn labeler(id, v) -> Option<String>` that returns names for one id and
   `None` for another; in `api.rs`'s test module extend `format_scalar_value_utf8_all_variants`;
   in `registry.rs`'s `formatted_parity_across_all_variants` add a `Dynamic` case.
2. Add the type alias + variant; change the two formatter signatures; add the arm.
3. Update `rows.rs` (`format_scalar_value(&opt.id, current, format)`) and `registry.rs`
   (`format_scalar_value_utf8(&opt.id, value, *format)`), plus every test call site
   (`fmt` helper in `scalar_format_tests.rs`, api tests, registry tests).
4. `cargo check --target x86_64-pc-windows-msvc`, `./scripts/validate_custom_options.sh`,
   `cargo fmt`.

## Acceptance Criteria

1. **Dynamic label hit**
   - Given a `DynamicLabelFn` returning `Some("EMI #2")` for `("background_dancer", 2)`
   - When `format_scalar_value("background_dancer", 2, ScalarFormat::Dynamic(f))` runs
   - Then the result is `b"EMI #2"` and the UTF-8 twin returns `"EMI #2"`

2. **Fallback on `None`**
   - Given the same labeler returning `None` for value 99
   - When formatted
   - Then the result is `b"99"` (plain integer)

3. **Id dispatch**
   - Given a labeler that returns different names for `"background_dancer"` and `"background_stage"`
   - When both ids are formatted with the same value
   - Then each id's own name is returned

4. **Existing variants unchanged**
   - Given every pre-existing `ScalarFormat` variant and the existing byte pins
   - When the suite runs after the signature change
   - Then every existing assertion still passes with the id argument added

5. **Both menus agree**
   - Given a registered `Dynamic` scalar option in `FrameworkState`
   - When `overlay_snapshot_rows` builds the overlay row
   - Then `formatted == format_scalar_value_utf8(id, value, format)`

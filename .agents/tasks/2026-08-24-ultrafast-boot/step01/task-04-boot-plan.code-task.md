# Task: Boot plan layer (plan.rs::compute)

## Description
Implement the pure boot-plan computation `plan::compute` in
`src/mods/fast_bootup/plan.rs`: given the work-list items, the identity
verdict map, and the loaded cache, decide per item Replay-vs-Stock and per
file-record whether it is eligible for the status 1→6 flip, enforcing the
safety invariants from the design.

## Background
A song's 5 work items share one file record (refcount 5). Flipping a record
that a stock item still needs would make that item analyze an emptied buffer
— triggering the game's ME1529 corruption reporter (a hard boot blocker).
This layer computes the plan so that the unsafe onUpdate orchestration (later
step) cannot make that mistake.

## Technical Requirements
1. Input types (plain, no game pointers): `WorkItem { entry_index: i32, difficulty: i32, mcode: i32 }`,
   a verdict lookup (game_path → Hit(file_key) | Miss), and a way to map an
   item to its game_path/file (provided by the caller as a resolved list so
   this layer stays pure).
2. Output `BootPlan { items: Vec<ItemPlan>, flips: Vec<i32> }` where
   `ItemPlan = Replay { /* payload handle */ } | Stock`.
3. Invariants (enforced and tested):
   - The final work item is ALWAYS `Stock`.
   - Items with `entry_index <= 0` are ALWAYS `Stock` (the game uses -1 for
     unregistered charts).
   - An `entry_index` appears in `flips` ONLY IF every item referencing it is
     `Replay` AND none of them is the final item.
   - A mixed hit/miss song (some items Replay, some Stock) never flips its
     shared record.
4. Split-file songs (distinct `entry_index` per difficulty) are handled
   naturally by the per-entry_index grouping — no special casing.
5. Pure: deterministic over its inputs, no I/O, no statics.

## Dependencies
- task-02 (cache/verdict types), task-03 (payload type referenced by ItemPlan)

## Implementation Approach
1. Group item indices by `entry_index`.
2. Mark every item Replay/Stock from the verdict + cache presence.
3. A record is flip-eligible iff all its items are Replay and the final
   work-list index is not among them.

## Acceptance Criteria

1. **Final item always stock**
   - Given any work list (even all-hit)
   - When planned
   - Then the last item is `Stock` and its record is not in `flips`

2. **Shared-record safety**
   - Given a 5-item song with 4 hits and 1 miss
   - When planned
   - Then all 5 items keep their individual Replay/Stock verdict BUT the shared entry_index is absent from `flips`

3. **Split-file independence**
   - Given a song whose 5 difficulties are 5 distinct entry_indexes, all hits, none final
   - When planned
   - Then each record is independently flip-eligible

4. **Unregistered charts**
   - Given items with `entry_index <= 0`
   - When planned
   - Then they are `Stock` and never contribute a flip

5. **Host tests in-module**
   - Given `cargo test`
   - Then all invariant cases pass

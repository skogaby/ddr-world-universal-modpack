## Background
The replay path (Step 7) writes into the music DB and releases loader entries
through the game's own functions. Per the repo's no-hardcoded-offsets rule,
those addresses are decoded from instructions inside onUpdate rather than
scanned as absolute values. All four sites were confirmed byte-exact on
gamemdx 20260721 (see the design's derivation table and the disassembly in
docs/ultrafast_boot_research.md §2).

## Technical Requirements
Confirmed anchors within the onUpdate body (file-relative, 20260721):
1. **music_db_global** = `&DAT_1806f2d78`: first `MOV RCX,[rip]`
   (`48 8B 0D`) in the body; decode disp at site+3. Validate: target inside
   module data AND != `step_data_global_table` (the manager, which shares the
   opcode later in the body).
2. **variable_bpm_threshold** = `&DAT_180393f40`: the unique
   `MOVSD XMM8,[rip]` (`F2 44 0F 10 05`); decode disp at site+5.
3. **find_music_by_mcode** = `0x1801b4290`: locate the unique
   `MOV byte ptr [RAX+0x1b0],1` (`C6 80 B0 01 00 00 01`); the immediately
   preceding 5 bytes are `E8 <rel32>` — decode_call_rel32(site-5). Validate
   byte at site-5 == 0xE8.
4. **step_data_release** = `0x1801ff1b0`: the `MOV RCX,[rip]` (`48 8B 0D`)
   whose decoded target == `step_data_global_table` AND whose site+7 byte ==
   `0xE8`; decode_call_rel32(site+7).

Use the existing scanner primitives (`scan_pattern_all`,
`decode_rip_relative`, `decode_call_rel32`). Bound the scan to a window over
the onUpdate body (~0xC00 bytes). Each derivation logs `[+] name @ +0xOFFSET`
on success and `[-] name -- reason` on failure; a failure inserts nothing
(soft — Step 7 gates on presence).

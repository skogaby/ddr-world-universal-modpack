# Task: Loader pacing raise + boot-pass measurement

## Description
In `src/mods/fast_bootup/mod.rs`, raise the step-data manager's per-pump open
cap (`mgr+0x70`, stock 4) to 64 for the duration of the boot pass and restore
it afterward, and add one-shot INFO instrumentation (begin/complete + item
count + elapsed) so the SSQ-window duration is measurable. This is the "load
as fast as the disk allows" half for cache misses (FR-6).

## Background
Boot loading is pacing-bound: the pending pump issues at most `mgr+0x70`
new file opens per pump and the app tick pumps once per frame (~4×fps
opens/s). Raising the cap lets the manager's I/O worker saturate the disk.
The cap is a plain ctor default (design §Data Models → manager +0x70),
safe to widen while the boot actor is live. We do NOT pump ourselves.

## Technical Requirements
1. On the FIRST hooked onUpdate call of a boot: read the stock cap at
   `*(*step_data_global_table + 0x70)`, store it, write the desired value;
   stamp a start `Instant`; log `boot pass begin -- open cap N->M`.
2. On completion (actor done flag `+0x20 & 0x24` observed set after the batch
   loop): restore the stock cap; log `boot pass complete -- processed X items
   in Y ms (open cap restored)`. One-shot per boot.
3. `disable()` restores the cap if it was raised and not yet restored.
4. Desired cap default 64. A dev-only env override
   `DDR_FAST_BOOT_OPEN_CAP` (parsed once; invalid/unset → 64) allows an A/B
   pacing measurement on one build — NOT operator config (mirrors the repo's
   `DDR_*` dev-env pattern), not written to mod-config.json.
5. All memory access null-guarded; restore idempotent; no panics across the
   hook boundary.

## Dependencies
- Step 2 (`step_data_global_table` already resolved; cap lever uses it)

## Implementation Approach
1. Add statics: cap-raised / cap-restored latches, stored stock cap, boot
   start `Instant`, processed-item accumulator.
2. `set_open_cap()` / `restore_open_cap()` helpers over
   `*(GLOBAL_TABLE_PTR as *const *const u8) + 0x70`.
3. Wire both into `update_hook` (raise before the loop on first call; restore
   after the loop when done) and `disable()`.

## Acceptance Criteria

1. **Cap raised then restored**
   - Given a boot with the mod enabled
   - When the boot pass runs and completes
   - Then the log shows begin (cap 4→64) and complete (cap restored) exactly
     once, and no post-boot loads run at the raised cap

2. **Measurable speedup**
   - Given cap 64 vs cap 4 (`DDR_FAST_BOOT_OPEN_CAP=4`) on the same build
   - When each boots
   - Then the "processed X items in Y ms" line quantifies the SSQ window and
     cap 64 is materially faster (or, if not, documents that the device is
     the bound → informs whether Appendix B's bounded drain is needed)

3. **Fail-open**
   - Given a null manager pointer
   - Then the cap logic no-ops without panic and boot proceeds

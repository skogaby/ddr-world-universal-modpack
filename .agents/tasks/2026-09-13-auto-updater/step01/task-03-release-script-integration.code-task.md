# Task: Build and ship the updater from the release archive script

## Description
Extend `scripts/build_release_archive.sh` so the one script the maintainer runs
at release time also cross-builds the updater for Windows 7, places
`ddr_world_hook_updater.exe` at the zip root beside the DLL, and refuses to
produce an archive if either binary carries the Win7-incompatible `ProcessPrng`
import. Also correct the script's stale comment about `data_mods` exclusions.
From this task on, every later step's updater goes through the real packaging
path.

## Background
Releases are published as a single flat zip (root = game folder) built by
`scripts/build_release_archive.sh`: it cross-builds the DLL for the tier-3
`x86_64-win7-windows-msvc` target with `-Z build-std=std,panic_abort` (the
default msvc target imports `bcryptprimitives!ProcessPrng`, absent on Windows 7,
and the loader rejects such binaries), stages `mod-config.json`,
`judgement_offsets.csv`, `README.md` and `data_mods/`, then zips. The updater
self-updates by being part of that zip, so the script must produce it with the
same recipe.

The script's comment block claims `_cache/`, `*_ifs/` and `*.arc` are excluded
from `data_mods`, but the `rsync` only excludes `.DS_Store`. That is harmless
today (a checkout never contains `_cache/` or `*.arc`, and the committed
`*_ifs/` directories under `custom_options`, `custom_folders`, `custom_series`
and `music_wheel_song_length` are intended shipping content generated by
`scripts/gen_option_labels.py`), but the comment misleads the next reader.

## Technical Requirements
1. `scripts/build_release_archive.sh` gains an `==> Building Windows 7 updater`
   block after the DLL build: runs
   `cargo xwin build --release --target x86_64-win7-windows-msvc -Z build-std=std,panic_abort`
   with the working directory `updater/` (use a subshell `(cd updater && …)`),
   then asserts
   `updater/target/x86_64-win7-windows-msvc/release/ddr_world_hook_updater.exe`
   exists (same error style as the DLL check).
2. Staging copies the exe into `$STAGE/` beside the DLL so it lands at the zip
   root.
3. A guard function (e.g. `assert_win7_safe <binary>`) runs on BOTH the DLL and
   the exe before zipping: it fails the script with a clear message if
   `strings "$1" | grep -q ProcessPrng`. Use `strings` (present on macOS and
   Linux); print the offending binary's path relative to the repo root.
4. Replace the stale comment above the `rsync` with an accurate one: only
   `.DS_Store` is excluded; `_cache/` and `*.arc` never exist in a checkout
   (runtime-generated on cabinets, `*.arc` is gitignored); the committed
   `*_ifs/` directories are shipping content. Keep the `rsync` invocation
   itself unchanged.
5. Update the header comment (`# Build a GitHub release archive containing…`)
   to mention the updater exe, and extend the final `unzip -l | tail` echo so
   the exe's presence is visible (e.g. `unzip -l "$ARCHIVE" | grep -E
   'ddr_world_hook(_updater\.exe|\.dll)$'`).
6. `bash -n scripts/build_release_archive.sh` passes; the script keeps
   `set -euo pipefail` semantics (no unguarded pipelines that would trip
   `pipefail` when `grep` finds nothing — the guard must treat "no match" as
   success).
7. Run the full script once and confirm: it succeeds, the zip root lists
   `ddr_world_hook.dll`, `ddr_world_hook_updater.exe`, `mod-config.json`,
   `judgement_offsets.csv`, `README.md`, `data_mods/`, and the file count is
   the previous count + 1. Temporarily point the guard at a binary known to
   contain `ProcessPrng` (e.g. a quick host-target `cargo build` of the updater
   for `x86_64-pc-windows-msvc` via `cargo xwin`) to prove the guard fires,
   then remove that scratch build.
8. Do not write machine-specific absolute paths into the script or any tracked
   file; the generated zip stays untracked (it already is — `*.zip` is not
   ignored, so do not `git add` it). Do not commit.

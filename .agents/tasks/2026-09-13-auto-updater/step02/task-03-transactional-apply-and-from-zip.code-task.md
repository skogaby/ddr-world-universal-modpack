# Task: Transactional apply with rollback, and the `--from-zip` install mode

## Description
Add `apply.rs` (journal, backups, plan execution by rename, same-run rollback,
cleanup) and wire `--from-zip <path> [--tag]` and `--force` into `main` so the
updater can install a release archive from disk end to end. Add the temp-dir
integration test harness the later steps extend.

## Background
Design §6 (ordering, per-action semantics, rollback), §4.11, §4.13 summary
line, §2.6 exit codes. Journal is written before the first mutation and deleted
after the manifest write (crash RECOVERY arrives in Step 5). `--from-zip`
records tag `local:<first 12 hex of the zip's sha256>` unless `--tag` is given;
asset name = file name; digest computed locally. Dev-only fault injection via
the `DDR_UPDATER_FAULT` env var (`apply-after:<n>` fails after n actions;
`rollback` makes the first restore fail) follows the DLL's `DDR_*_FAULT`
precedent so rollback paths can be exercised by tests.

## Technical Requirements
1. `apply.rs`: `Journal { tag, started_unix, actions }` written to `journal.json`; `execute(game, plan, stage_root, merged, manifest) -> Result<Summary, ApplyError>`; `backup/` emptied at start; `Write{existed:true}` = rename target→backup (mirrored path) then rename stage→target; `Write{existed:false}` = rename stage→target; `Prune` = rename target→backup; `WriteMerged` = write `.tmp`, back up original, rename into place; `WriteManifest` = temp+rename LAST; then delete journal, `download/`, `stage/`. On error: reverse walk restoring backups / deleting new files; `ApplyError::RolledBack(cause)` vs `ApplyError::RollbackFailed{cause, restore_errors}`. `Summary { written, pruned, kept_modified, merged_written }`.
2. `main.rs`: for `Run` with `from_zip`: verify file exists → sha256 → tag → read manifest (Err → WARN, treat absent) → `needs_update` (respect `--force`) → "up to date (tag)" `NothingToDo` when not needed → extract → hash tree → `MergedFiles` (copy release copy iff user file absent) → plan → execute → summary line (§4.13 wording) → `Outcome::Ok`; any failure before apply → one-line "skipped (reason)" `Skipped`; `RolledBack` → "update failed and was rolled back (reason)" `Skipped`; `RollbackFailed` → `Outcome::RollbackFailed` + list unrestored files + backup path.
3. Integration tests `updater/tests/apply_e2e.rs` (synthetic game folder + zip built in a temp dir): first run installs (shipped replaced, user/_cache/generated untouched, manifest correct, backup holds originals, download/stage gone, journal gone); second identical run → "up to date"; `--force` re-applies; second run with a zip dropping one file and modifying another → prune / keep; injected failure (`DDR_UPDATER_FAULT=apply-after:2`) → folder byte-identical, exit 0; `DDR_UPDATER_FAULT=rollback` → exit 1 with backup path in output; missing user `mod-config.json` → copied from release; present → untouched.
4. Remove the Step-1 `#[allow(dead_code)]` markers that are now consumed.

## Acceptance Criteria
1. **Install** — Given a synthetic game folder and release zip — When `--from-zip` runs — Then release-owned files are replaced, user/runtime files untouched, manifest written, exit 0.
2. **Idempotent** — Given the manifest matches the zip — When run again — Then "up to date", nothing changes, exit 0; `--force` reinstalls.
3. **Prune / keep** — Given a previous manifest with a dropped file — When updating — Then unchanged dropped files are removed, locally modified ones kept and reported.
4. **Rollback** — Given an injected mid-apply failure — When the run ends — Then every file is byte-identical to before, exit 0.
5. **Rollback failure** — Given an injected restore failure — When the run ends — Then exit 1 and the console names the backup directory.

# Task: judge_submit tap block for S-Marvelous classification

## Description
Add the S-Marvelous classification block to the existing `judge_submit` detour
body in `src/mods/power_user_statistics/data_feed.rs`, feeding
`s_marvelous::state` — the calibration-tap precedent: the detour body is the
only place the per-step ms error exists (one detour per target), and all
policy stays in the mod.

## Background
The hook (`judge_submit_hook`, src/mods/power_user_statistics/data_feed.rs)
already computes everything needed: `grade_index = judge_code - 0x1028`
(accepted `<= 6`), `player_side = *(actor + 0x84)`, and
`ms_error = *(scratch + 4)` (present for every grade except O.K., whose
`has_ms_error` is false). The S-Marvelous block additionally needs the live
combo counter `*(actor + 0x1DC)` (GamePlayActor field map:
docs/s_marvelous_judgement_research.md §2.1) — read ONLY when the side is
armed, keeping the disarmed cost at one relaxed load. The block must run for
ALL grade opcodes 0..=6 (the combo-bit machine needs grades 1..6 too, and the
O.K. case passes `ms: None`), positioned like the existing calibration tap
(after the side validity check; independent of the `try_lock` buffer path so
a contended lock cannot drop S-Marv events).

## Technical Requirements
1. In `judge_submit_hook`, inside the existing `player_side <= 1` branch, add
   the S-Marvelous block:
   - Guard: `s_marvelous::state::is_armed(player_side)` (one relaxed load when
     disarmed — the ONLY cost with the mod off/disarmed).
   - When armed: read `combo = *(actor.add(0x1DC) as *const i32)` and call
     `s_marvelous::state::on_judge_event(player_side, grade_index,
     ms: has_ms_error ? Some(ms_error) : None, combo)`.
   - The block must see every grade opcode 0..=6 — place it so it runs for
     both the `has_ms_error` and O.K. paths (i.e., not nested inside the
     `has_ms_error` branch).
2. Introduce a named constant for the combo offset
   (`ACTOR_COMBO_OFFSET: usize = 0x1DC`) beside `ACTOR_PLAY_SIDE_OFFSET`.
3. No locks, no allocation, no logging on the hot path; no behavior change to
   any existing consumer (calibration tap, buffers, CSV, widget update).
4. Keep the module doc comment's consumer list accurate (mention the
   S-Marvelous tap alongside the calibration tap).

## Acceptance Criteria

1. **Disarmed cost**
   - Given no side is armed
   - When any judgement dispatches
   - Then the added code performs exactly one relaxed atomic load per event
     and touches nothing else

2. **Armed classification**
   - Given side 0 armed with window 12
   - When a grade-0 event with ms in [−12, +12] dispatches for side 0
   - Then `smarv_count(0)` increments (verified by code inspection against the
     task-01 tests; live verification is task-03's demo)

3. **All grades reach the state machine**
   - Given an armed side
   - When grade 1..=5 events and a grade-6 (O.K.) event dispatch
   - Then `on_judge_event` is invoked for each (O.K. with `ms == None`)

4. **No regression**
   - Given the existing PUS/calibration behavior
   - When the block is added
   - Then calibration counters, MsError buffers, CSV capture, and the widget
     update are byte-for-byte unaffected code paths, and
     `cargo check --target x86_64-pc-windows-msvc` is clean

## Technical Requirements
1. Define the fixed-size `RedirectToken` with nonce/depth, generation, participant/stage identity, exact rate, and all four full digests from the approved design.
2. Implement four preallocated XACT slots with atomic phases `Free`, `Entered`, `Exposed`, `Committed`, `ReleasePending`, and `Quarantined`.
3. Implement per-thread bounded TLS frames with monotonically increasing nonce, nesting depth, file ID, slot reference, and a nonallocating guard that clears state on every exit.
4. Validate owner thread, nonce, depth, file ID, generation, path/cache/output digests, and legal phase CAS transitions before consuming a token.
5. Provide owner/nonce slot recovery when exact TLS state is unavailable; ambiguity or overflow must reject rate handling and retain identity.
6. Store/transfer Step 2 lease IDs without cloning lease handles and preserve process pins for future late-failure handling.
7. Add a fixed/preallocated maintenance event queue for unload release and quarantine work; full queues conservatively retain slots/leases rather than overwrite events.
8. Keep hot-path operations allocation-free, lock-free, I/O-free, JSON-free, and panic-free after construction.
9. Keep all exposure/commit entry points inaccessible to normal runtime policy in this task; tests may exercise primitives directly.

## Acceptance Criteria

1. **Exact Nested Call Isolation**
   - Given nested and reentrant frames on one thread
   - When tokens are stored and consumed
   - Then each nonce/depth/file identity resolves only its own frame and all guards clear deterministically

2. **Concurrent Slot Safety**
   - Given calls on multiple threads up to and beyond four slots
   - When slots are claimed and transitioned
   - Then legal calls remain isolated, overflow falls back to identity, and no slot is double-owned

3. **TLS Recovery and Ambiguity**
   - Given missing/corrupt TLS after a known exposure
   - When owner/nonce recovery runs
   - Then one exact slot is recovered or the operation fails closed without selecting a candidate heuristically

4. **Bounded Maintenance Queue**
   - Given release/quarantine events through and beyond queue capacity
   - When producers enqueue and the worker drains
   - Then FIFO events retain complete identities, saturation overwrites nothing, and rejected events leave resources pinned

5. **Hot-Path Constraints**
   - Given allocation/lock/I/O probes around every slot/TLS/queue operation
   - When stress tests run
   - Then no prohibited operation occurs and identity publication remains unchanged

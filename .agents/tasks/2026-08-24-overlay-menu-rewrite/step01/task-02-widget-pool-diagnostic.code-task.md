# Task: Widget-pool boot diagnostic

## Description
Add a one-shot boot-time diagnostic to `src/services/widget_renderer.rs` that walks the
game's render-list free-node pool and logs the available node count. The overlay-menu
rewrite raises the repo's worst-case widget consumption from ~49 to ~63 nodes against a
pool of unknown size; this diagnostic turns that unknown into a logged number.

## Background
Widget nodes come from a game-side pre-allocated free pool at `*(scene_manager+0xB0)`;
nodes are permanently consumed (destroy only hides). Exhaustion is non-fatal (WARN +
invisible widget) but silent. The pool structure is fully mapped in
`docs/widget_registration_system.md` (§ list-manager layout: free-list head, sentinel
node). The registration code in `register_in_render_list`
(`src/services/widget_renderer.rs`) already reads the free head and sentinel — reuse its
exact pointer arithmetic and validation style.

## Technical Requirements
1. New function in `widget_renderer` that walks the free list from the free head to the
   sentinel, counting nodes, with a hard iteration cap (e.g. 4096) against a corrupted
   list, and every pointer read null/range-guarded (fail-open: log "unavailable" rather
   than crash).
2. Runs exactly once, after the widget system is initialized (the render-list manager
   pointer must be resolved), on the render thread or wherever the manager pointer is
   already legally read — match the existing code's access pattern.
3. Emits one `log_info!` line, e.g. `widget_renderer: render-list free pool: N nodes
   available` (or `: free pool walk unavailable (reason)`).
4. No behavior change to widget creation/registration.

## Dependencies
- task-01 (clean tree; no code dependency).

## Implementation Approach
1. Locate the free-head/sentinel reads in `register_in_render_list`; factor the pointer
   plumbing into the walk without disturbing the registration path.
2. Trigger the one-shot from the first wrapper-render pass after init (a `Once` or
   AtomicBool guard), since the manager pointer is guaranteed live there.
3. Validate via a local CrossOver boot run: the INFO line appears in the log with a
   plausible count.

## Acceptance Criteria

1. **Count logged on healthy boot**
   - Given a normal game boot with the DLL loaded
   - When the widget system initializes
   - Then exactly one INFO line reports the free-node count.

2. **Fail-open on unavailable state**
   - Given the render-list manager pointer is null or the walk exceeds the iteration cap
   - When the diagnostic runs
   - Then it logs one "unavailable" line and widget creation continues unaffected.

3. **Readiness gate**
   - Given the change
   - When `cargo check`, `cargo fmt`, `./build.sh` run
   - Then all pass.

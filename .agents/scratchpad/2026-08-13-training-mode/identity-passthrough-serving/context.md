## Mapping semantics (design §4.5 / research §5.1)

Virtual main-entry block `v`:
- `v < lead_blocks` ⇒ the entry-format pre-encoded silent block
- else served-stream block `v − lead_blocks + shift_blocks`
- silent tiling past the content end
Blocks are in the entry's SERVED stream domain (== source blocks at
identity; == stretched output blocks at rate). Content→block conversion is
the caller's job (Steps 2–3). The virtual layout (header) NEVER changes —
the engine parses it once per bank (research §5.1).

## Assumptions / decisions (auto mode)

- Mapping storage: ONE packed AtomicU64 (shift:u32 hi | lead:u32 lo) +
  `mapping_epoch: AtomicU64` — a torn-shift/lead pair from two separate
  atomics could serve a mixed mapping; the design's "two AtomicU64" is a
  field-shape suggestion, behavior binding (same precedent as the Ring
  `base` cursor omission recorded at breakdown approval). API stays
  block-unit `(u64, u64)`.
- Identity bindings use a minimal ring allocation (the ring is never read
  in that mode) — 16 MiB per identity arm would be waste.
- `set_content_mapping` on a Stretch binding does NOT itself bump the ring
  seqlock; the generator's remap restart calls `ring_rewind` (the AGENTS
  gotcha's "reuse the existing behind-window machinery"). Contract: mapping
  changes happen with the cue stopped (bind time / stop→replay window).
- `GeneratorCore::new` refuses IdentityPassthrough bindings (defensive; the
  task-02 prepare path simply never spawns for them).

## Clearing-semantics rationale (from the task Background — load-bearing)

- TRAINING rides `reset_song_taint()` (per-song): a triple-1 restart clears
  it; task-02's `on_song_reset(t>0)` subscriber re-taints when the restart
  actually seeks to a marker. Producers all fire frames AFTER the scene
  change, so the scene-callback clear cannot race them.
- ASSIST_TICK must NOT be cleared by `reset_song_taint()`: it is level-written
  at every GAMEPLAY entry by assist_tick's own latch (task-02), and clearing
  it from quick_restart's scene callback would create a cross-mod
  callback-ORDER dependence. Same shape as autoplay's live mirror.
- `reset_session()` (card-in) clears both for the next player.

## Ambiguities / assumptions (auto mode record)

- The task says tests "must restore [statics] or the suite must stay
  order-independent". The existing suite has no test lock; the new tests
  mutate BOTH sides' taints and `QUICK_FAIL_TAINT`. Decision: add a private
  `static TAINT_TEST_LOCK: Mutex<()>` used by every new global-state test
  (and leave the existing rate test alone — it only touches side 1's rate
  ledger, which the new tests don't touch). Each new test restores clean
  state before releasing the lock (poisoning handled via
  `unwrap_or_else(PoisonError::into_inner)` so one failure doesn't cascade).
- "One-way per song, idempotent" for `set_training_taint` = plain
  `store(true)`; no toggle-off setter exists by design (only the resets clear
  it).

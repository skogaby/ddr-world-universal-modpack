## THE EXPLORE QUESTION — Session vs None (settled)

**Finding: `PersistMode::None` is NOT the needed behavior. No halt required; add `Session`.**

- `None` has **zero registered users** (only the unused `no_persist()` builder
  references it). Its doc comment claims "the value resets to `default_value` on
  every card swipe" — **no code implements that reset anywhere**. Searched:
  registry.rs, mod.rs, custom_options_persistence.rs — there is no card-in
  value-reset mechanism at all. The in-memory per-side cache lives for the
  process lifetime (arcade cabinets stay up across card swaps), so a `None`
  value set by player A would leak into player B's session. The doc claim is
  historical fiction from the `persist: false` era.
- Actual `None` behavior today: excluded from network save
  (`snapshot_for_save` filters `!= None`), excluded from network load + JSON
  prime (`resolve_from_load` gates `== Full`), excluded from JSON write
  (`json_persisted` gates `== Full`). No reset.
- Needed `Session` = `None`'s exclusions **plus a real card-in reset**. The
  difference is real; the design names `Session` explicitly. Also fix `None`'s
  false doc while touching the enum (doc-truth fix, no semantic change).

## Card-in reset hook placement (maintainer decision: "same profile-load lifecycle point where Full values land; one registry-side hook")

Full values land: `load_receiver_trampoline` (ess.dll detour) captures values +
ddrcode → `PENDING_LOADS` → drained at SONG_SELECT entry by
`apply_pending_loads` → `resolve_from_load` per resolved side.

BUT `apply_pending_loads` only fires when the response carried mod values AND
`persist_network` is on — a fresh profile or gated cabinet would never reset
Session rows. The sibling drain `apply_pending_rate_resets` (same scene
callback, runs first, lines 290–295) fires for **every successful card-in load**
(ddrcode captured unconditionally at load_receiver_trampoline:1092–1100,
"deliberately independent of the persist_network gate") and resolves the side
by ddrcode — it is the codebase's established per-side card-in reset (song-rate
ledger). That IS the same lifecycle point, with the correct always-fires signal.

Implementation: kernel method `FrameworkState::reset_session_values(side) ->
Vec<(OnChangeFn, u8, i32)>` (host-testable; resets `persist.session_scoped()`
options whose side value differs from default; returns callback tuples), a
`pub(crate) custom_options::reset_session_values(side)` wrapper (lock, then
dispatch after release — the `resolve_from_load` pattern), called from
`apply_pending_rate_resets` beside `score_guard::reset_rate_state_for_side`.

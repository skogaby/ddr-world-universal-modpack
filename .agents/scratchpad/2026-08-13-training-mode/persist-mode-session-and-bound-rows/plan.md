## Test scenarios (written first, against the harness registry kernel)

New harness-mounted file `src/services/custom_options/persist_matrix_tests.rs`
(mounted in the harness `main.rs` beside `availability_tests.rs`).

1. **Persistence matrix is exhaustive and correct** (AC 1 + AC 4)
   - For each mode assert the `(saved_to_network, loaded_from_network,
     json_cached)` tuple: Full `(t,t,t)`, SaveOnly `(t,f,f)`,
     None `(f,f,f)`, Session `(f,f,f)`; `session_scoped()` true only for
     Session. Pins existing modes (unregressed) AND Session's exclusions —
     the three mod.rs choke points consume exactly these methods, so "no wire
     field / no cache entry / load never touches it" follows structurally.
2. **Save-snapshot filter excludes Session** (AC 1)
   - Kernel-level replica of `snapshot_for_save`'s filter over a
     FrameworkState holding one option per mode with non-default values:
     only the Full + SaveOnly ids appear.
3. **Card-in reset, per side** (AC 2)
   - Session row set to 500 on side 0 (side 1 default), Full row set to 150
     on side 0. `reset_session_values(0)`: Session side 0 back to default,
     side 1 untouched, Full untouched; returned callback tuple ONLY for the
     changed Session row `(side 0, default)`.
   - `reset_session_values(1)` with side 1 already at default returns no
     callbacks (no-op resets don't dispatch).
4. **Load-side gate rejects Session** (AC 1)
   - Kernel-level: the resolve gate (`loaded_from_network()`) is false for
     Session ⇒ a simulated load application skips the row, value unchanged.
5. **Existing suites unregressed** (AC 4) — full harness run stays green
   (baseline 210), availability_tests untouched.

Row registration (AC 3) is engine-facing (row injection, textures) —
cabinet-validated at the Step-3 demo per repo law; host coverage of it is the
kernel registration path already exercised by scenario 2/3 specs.

## Implementation approach

1. **api.rs** — add `Session` to `PersistMode` (doc: the full contract + the
   updated matrix table incl. card-in reset column); add exhaustive-match
   methods `saved_to_network()`, `loaded_from_network()`, `json_cached()`,
   `session_scoped()` (no `_` arms); correct `no_persist()`'s false
   reset-on-card-swipe claim.
2. **registry.rs** — `FrameworkState::reset_session_values(side) ->
   Vec<(OnChangeFn, u8, i32)>`: for each option with `persist.session_scoped()`
   and `values[side] != default`… note: the kernel does NOT store
   `default_value` today — add a `default_value: i32` field to
   `RegisteredOption` (captured from the spec at registration) so the reset
   can restore it. Append-only struct change, no behavior change elsewhere.
3. **mod.rs** — convert the three choke points to the matrix methods; add the
   `pub(crate) fn reset_session_values(player_side: u8)` wrapper (lock →
   collect → dispatch after release, `resolve_from_load` pattern; one INFO
   when anything reset).
4. **custom_options_persistence.rs** — in the SONG_SELECT card-in drain
   (`apply_pending_rate_resets`, renamed `apply_pending_card_in_resets` for
   doc-truth), call `custom_options::reset_session_values(side)` beside the
   rate-ledger reset.
5. **training_mode** — `bounds.rs`: `ROW_SKIP_FIRST`/`ROW_OMIT_LAST` per-side
   AtomicI32s (seconds domain) + `row_skip_first(side)`/`row_omit_last(side)`
   accessors (task-02 consumes) + on_change fns. `mod.rs`: register the two
   Session scalar rows in `enable()` behind `row_injection_available()`
   (WARN + continue on unavailability — gestures still work), seed atomics,
   `set_option_available(true)`; `disable()`: available(false) + zero atomics.
6. **Textures** — LABELS + PREVIEWS entries in `scripts/gen_option_labels.py`;
   run it; verify the 4 new PNGs exist in-repo.
7. **Harness** — mount `persist_matrix_tests.rs`; full gates.

## Risks

- `RegisteredOption` gains a field — compile-time enforced at the single
  construction site; no layout hazard (pure Rust state, not game memory).
- The rename of `apply_pending_rate_resets` is internal (one caller).
- Session rows + `snapshot_for_save`: the ONLY behavioral change to shipped
  saves is that a hypothetical `None` row would still be excluded — unchanged;
  Full/SaveOnly emission unchanged (scenario 2 pins it).
